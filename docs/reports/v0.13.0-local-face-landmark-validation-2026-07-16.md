# v0.13.0 Local Face Landmark Validation - 2026-07-16

## Summary

This report records a Windows local validation pass for Issue #536 (v0.13.0 local face landmark tracking vertical slice) against `origin/main` at `5c99bbc51cf43b00ec20505067905340d5f91754`.

- All required automated checks (`pnpm format:check`, `typecheck`, `build`, `lint`, `test`, and the individually-listed `test:*` scripts) pass on this machine once two known local/environment adjustments are applied (documented below).
- The opt-in real MediaPipe Face Landmarker runtime smoke (`pnpm smoke:mediapipe-face-landmarker-runtime:local`) reports `FAILED` (`worker_protocol_invalid`), not `PASSED` or `SKIPPED`.

- An isolation test (real OpenCV webcam + the non-MediaPipe `synthetic-frame-helper` backend) confirms the camera, private frame transport, and helper lifecycle plumbing itself works correctly on this real hardware; the defect is scoped specifically to real MediaPipe's native library stderr output.

## Real MediaPipe Runtime Smoke

Command shape (paths redacted):

```text
LVK_MEDIAPIPE_SMOKE=1
LVK_MEDIAPIPE_SMOKE_PYTHON=<absolute-path-to-mediapipe-venv-python>
LVK_MEDIAPIPE_MODEL_ASSET_PATH=<absolute-path-to-face_landmarker.task>
pnpm smoke:mediapipe-face-landmarker-runtime:local
```

Result: **FAILED**, `reason: worker_protocol_invalid`.

Direct investigation (running the underlying Python worker module manually, capturing stdout and stderr separately) showed that the real MediaPipe inference actually succeeds:

```json
{
  "schemaVersion": 1,
  "check": "mediapipe-face-landmarker-runtime-smoke",
  "status": "PASSED",
  "reason": null,
  "pythonVersion": "3.11.4",
  "mediapipeVersion": "0.10.35",
  "inputCategory": "synthetic-solid-bgr24",
  "inputWidth": 64,
  "inputHeight": 64,
  "runtimeCreationStatus": "success",
  "inferenceStatus": "success",
  "inferenceMs": 16.0,
  "payloadStatus": "lost",
  "closeStatus": "closed"
}
```

but the same process also writes several benign native-library diagnostic lines directly to stderr (glog/absl-style log lines from MediaPipe's C++ graph, e.g. an XNNPACK delegate creation notice and a blendshape-acceleration-mode notice). `tools/check-mediapipe-face-landmarker-runtime-smoke.mjs` requires the spawned worker's stderr to be exactly empty (`if ((result.stderr ?? "") !== "") { ...worker_protocol_invalid }`), so it reports `FAILED` even though the real inference genuinely passed.

Standard suppression environment variables (`GLOG_minloglevel`, `GLOG_v`, `TF_CPP_MIN_LOG_LEVEL`, `ABSL_MIN_LOG_LEVEL`) were tried and did not suppress this output — consistent with MediaPipe's C++ graph code using Abseil logging initialized inside the compiled native extension, not a Python-level or env-configurable logging path.

This checker behavior was not previously exercised end-to-end with genuine MediaPipe on real hardware (the prior validation machine reported `LVK_HAS_OPENCV_CAMERA=0` and never reached this code path), so this is a newly discovered gap, not a regression.

## Root Cause Finding (primary blocking finding)

The real Native Core webcam route was attempted with the fully configured `mediapipe-face-landmarker` backend:

```text
--tracking-backend mediapipe-face-landmarker
--camera-source opencv
--mediapipe-python <absolute-path-to-mediapipe-venv-python>
--mediapipe-helper-script <repo>/native/tracker-core/helpers/mediapipe_face_landmarker/face_landmarker_helper_session.py
--mediapipe-model-asset <absolute-path-to-face_landmarker.task>
```

- **Bare capability query** (`--print-runtime-capabilities`, no other flags): confirmed side-effect-free (`cameraOpened=false`, `motionFramesEmitted=false`, `helperLaunched=false`).
- **Configured capability query** (same flags as above, plus `--print-runtime-capabilities`): confirmed the route is recognized as fully configured (`mediapipeFaceLandmarkerHelperRouteConfigured=true`) while remaining side-effect-free.
- **Real launch attempt** (`--frames 30 --log-camera-status --log-pipeline-status ...`, no `--print-runtime-capabilities`): failed immediately with the generic diagnostic `Failed to start tracking backend: mediapipe-face-landmarker.`, zero MotionFrame lines on stdout, exit code 1. No camera was opened (no `[camera] startup:` diagnostic line appeared).

Source inspection (`native/tracker-core/src/helper_process_session.cpp`, `HelperProcessSession::drainStderr()`, approx. lines 2552-2591) shows that Native Core requires **every line** the Python helper process writes to stderr to begin with the literal prefix `"[helper] "`; any non-conforming line causes `drainStderr()` to return `false`, which fails the helper session and, through `trackingBackend->start()`, aborts the whole route before the camera opens or any MotionFrame is emitted. The Python helper script (`face_landmarker_helper_session.py`) does correctly emit its own diagnostics with this exact prefix (confirmed by source inspection) — but it never redirects or suppresses MediaPipe's own native (C++) library stderr writes, which happen at the OS file-descriptor level, outside the Python script's control, the moment the real Face Landmarker runtime is created. Those native library lines do not carry the `"[helper] "` prefix, so they trip the same fail-closed guard described in the runtime-smoke finding above — this time inside the production route itself, not just the standalone checker.

**This is the same underlying contract mismatch surfacing in two independent places**: the standalone runtime-smoke checker (requires empty subprocess stderr) and the real Native Core helper-session stderr validator (requires every stderr line to carry a specific prefix). Both reject real MediaPipe's own native diagnostic output. Fixing this would require a runtime source change (either loosening/allowlisting Native Core's helper-stderr contract for known-benign non-`[helper]`-prefixed lines, or having the Python helper redirect the native library's stderr file descriptor during Face Landmarker creation/use) — both out of scope for this validation-only task and requiring a scope amendment, per the task contract. No such change was made.

## Isolation Test: Camera/Transport/Lifecycle Plumbing (without real MediaPipe)

To determine whether the defect above is specific to real MediaPipe or reflects a broader architecture problem, the real OpenCV camera was exercised with the existing non-MediaPipe `synthetic-frame-helper` backend and the repository's own `lvk-synthetic-helper` executable:

```text
--tracking-backend synthetic-frame-helper --camera-source opencv
--helper-executable <built-synthetic-helper-exe>
--frames 15 --log-camera-status
```

Result: exit code 0. 15 valid MotionFrame v1 JSON lines on stdout (`schemaVersion:1`, `source:"native"`, clamped finite tracking/eyes/mouth values). Camera diagnostics on stderr showed a real webcam opened via the `MSMF` backend at `640x480`, nominal 30 FPS, effective ~13.8 FPS over the 15-frame bounded run, with clean startup and shutdown and `failedReadCount=0`.

This confirms the real OpenCV camera, the private frame transport pipe, and the helper process lifecycle (launch, ready handshake, per-frame request/result, clean shutdown) all function correctly end-to-end on this machine's real hardware. The blocking defect is scoped specifically to the interaction between real MediaPipe's native stderr output and Native Core's helper-stderr contract — not a general camera, transport, or lifecycle failure.

## Final Judgment

**Not ready with blocking findings.**

The v0.13.0 real MediaPipe Face Landmarker route cannot be demonstrated end-to-end on this dedicated local development machine with a real webcam, a real Python/MediaPipe environment, and a real local model asset: both the standalone opt-in runtime smoke and the real Native Core webcam route fail due to the same root cause — real MediaPipe's native library writes diagnostic lines to stderr that do not conform to Native Core's `"[helper] "`-prefixed helper-stderr contract, and neither existing surface tolerates that. Everything not dependent on this defect (environment gate, full automated baseline, build, capability queries, camera/transport/lifecycle plumbing via a non-MediaPipe backend, negative-path fail-closed behavior, cleanup, and local-only/privacy invariants) passed. A follow-up fix (either loosening/allowlisting the helper-stderr contract for benign native-library diagnostic lines, or having the Python helper redirect MediaPipe's native stderr during runtime creation/use) is required before this milestone can be re-validated; that fix is out of scope for this validation-only task and needs an explicit scope amendment.
