## Why this spike

The diagnostics evidence recorded in `docs/TRACKING_BACKEND_EVALUATION.md` (Pass 1–4) was collected
on 2026-06-16/17 and predates the helper-process H1/H2 work that has since landed on `main`. This
spike re-confirms the safe, camera-free baselines on the current tree and records the new evidence
that the recommended helper-process boundary has moved from design to a passing synthetic prototype
inside Native Core. The purpose is to state clearly what evidence exists for the next backend
decision and what remains gated.

## Environment

- OS / environment category: Windows 11 Pro (x86-64 developer workstation).
- Native Core build: pre-existing local `native/tracker-core/build/Release` binaries (OpenCV-enabled,
  dynamically linked to a local vcpkg OpenCV). No reconfigure or rebuild was performed in this spike.
- Runtime DLLs: `<vcpkg-root>/installed/x64-windows/bin` was placed on `PATH` before running the
  OpenCV-enabled `lvk-tracker-core.exe`. Without it the binary exits with `STATUS_DLL_NOT_FOUND`
  (`0xC0000135`); this matches the known Windows/vcpkg runtime note in
  `docs/LOCAL_RUNTIME_CHECKLIST.md`.
- Repository state: spike branch cut from `main` after the v0.3 calibration baseline (#403) merged.
  #403 changed Web Preview and tools only; Native Core source was unchanged, so the native evidence
  below reflects current `main` Native Core.

### 2. Dummy / noop finite diagnostics (camera-free)

```
lvk-tracker-core.exe --frames 5 --camera-source dummy --face-detector noop \
  --log-camera-status --log-face-status --face-status-interval 1 \
  --log-pipeline-status --pipeline-status-interval 1
```

- Exit code: 0.
- stdout: 5 valid MotionFrame JSON lines (`schemaVersion=1`, `source=native`).
- stderr: `[camera]`, `[pipeline]`, and `[face]` diagnostics only.
- Face diagnostics show the newer fields from the #391/#392 stabilization work:
  `hasFace=false`, `usedFallbackTracking` (false on the startup line, then true on periodic lines),
  and `resultSource=none` throughout. This is the expected noop baseline, not a failure.
- Pipeline timing: `totalFrameDurationMs` ≈ 0.93ms on the first frame (stdout/JIT warmup) then
  ≈ 0.03ms per frame afterwards; all stages sub-millisecond in dummy/noop mode.
- Camera shutdown reported `failedReadCount=0`.

### 3. Helper-process synthetic runtime smoke via `lvk-tracker-core` (camera-free)

The `--helper-runtime-smoke PATH` path runs an explicit synthetic helper integration smoke and
leaves default tracking unchanged when omitted. `PATH` points at the local `lvk-synthetic-helper`
executable built alongside the tracker.

```
lvk-tracker-core.exe --helper-runtime-smoke <lvk-synthetic-helper> --helper-runtime-smoke-case normal
lvk-tracker-core.exe --helper-runtime-smoke <lvk-synthetic-helper> --helper-runtime-smoke-case helper-lifecycle-handshake
```

- `normal`: exit 0. Emits synthetic MotionFrame JSON lines on stdout (`schemaVersion=1`,
  `source=native`, `status=tracking`).
- `helper-lifecycle-handshake`: exit 0. stdout emitted 0 MotionFrame lines; stderr recorded
  `[helper-runtime-smoke] helper lifecycle handshake observed; helper stream ... to Native Core`.
  Public stdout remained reserved for MotionFrame JSON.

### 4. Standalone helper synthetic smoke executables (camera-free)

These are standalone synthetic-only executables built from Native Core. None touch a camera, a
model, or the network.

| Executable                             | Result (exit 0)                                                                                                                                                                                                                                                  |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lvk-helper-result-mapping-smoke`      | Mapped 5 synthetic helper result cases to MotionFrame JSON (`tracking`, `lost`, `not_started`, populated rotation/eyes/mouth). `mappedCaseCount=5`.                                                                                                              |
| `lvk-helper-process-supervision-smoke` | `normal` (launched, exitCode=0, lifecycle markers, safe stderr), `failure` (handled non-zero exit), `timeout` (detected hang, terminated child), `high-volume` (bounded/truncated capture). All cases passed.                                                    |
| `lvk-helper-h2-state-machine-smoke`    | 11 H2 synthetic state-machine cases passed: startup timeout, unknown message type, malformed line, oversized-line rejected, graceful exit, shutdown-after-already-exited, failure/timeout fallback, forced exit, launch failure, unsafe-diagnostics fail-closed. |

The H2 state-machine transitions observed cover the full lifecycle the design requires, e.g.:

```txt
not_started -> launching -> waiting_for_ready -> ready -> running -> stopping -> exited   (graceful)
not_started -> launching -> waiting_for_ready -> timed_out -> fallback                     (startup timeout)
not_started -> launching -> failed -> fallback                                             (launch failure)
... running -> failed -> fallback                                                          (unsafe diagnostics, fail-closed)
```

## Backend decision implications

- The backend _direction_ question is effectively resolved in the current tree: the recommended
  path is the Native Core-owned **helper-process boundary**, and its synthetic prototype (H1 + H2
  synthetic smokes) now passes locally. The in-process MediaPipe C++ / ONNX route remains deferred
  (blocked in prior spikes), and OpenCV Haar remains a smoke/baseline only.
- The active boundary is **not** "which backend" but the **H2 production-runtime planning gate**.
  Per `TRACKING_HELPER_PROCESS_H2_PRODUCTION_RUNTIME_OWNER_DECISION_RECORD.md`, the H2 standalone
  synthetic-smoke vector phase is closed and production-runtime planning, production implementation,
  default `lvk-tracker-core` runtime wiring, real camera access, and any real-frame IPC all remain
  gated behind an explicit owner Option A / B / C decision.
- No production readiness is claimed by this spike. All evidence here is synthetic/dummy and
  camera-free.

## Recommended next issue

**Split a smaller follow-up before #400.** The evidence supports continuing on the helper-process
path, but the immediate blocker is the owner decision recorded in the H2 production-runtime owner
decision record, not missing diagnostics. The smallest useful next step is the explicit owner
Option A / B / C decision (and, if Option B, a docs-only production-runtime planning PR) before any
production/runtime implementation slice such as #400. Jumping straight to implementation would skip
the owner gate that current H2 docs require.
