## Architecture Decision (Issue #580)

Implemented a route-selected, bounded opaque private-stderr discard policy
inside the existing Native Core helper-session boundary:

```cpp
enum class HelperStderrPolicy {
  StrictPrefixedDiagnostics,
  BoundedOpaqueDiscard,
};
```

- `HelperSessionConfig::stderrPolicy` defaults to `StrictPrefixedDiagnostics`.
  This default, and its full existing behavior (bounded-line size, the
  required `"[helper] "` prefix, EOF residual validation, oversized-line
  rejection), is **unchanged** for every generic helper session, the
  synthetic routes, and the default tracker routes.
- **Only** `createMediaPipeHelperRouteConfig()` selects
  `HelperStderrPolicy::BoundedOpaqueDiscard`, for the explicit MediaPipe Face
  Landmarker development route only. `main.cpp` and `tracking_backend.cpp`
  never select it (verified both by dedicated C++ static-boundary smoke
  assertions and by the Node checker's static source guard, which fails the
  check if `BoundedOpaqueDiscard` appears in either file).
- Under `BoundedOpaqueDiscard`, child stderr bytes are treated as untrusted
  and opaque: never parsed, classified, echoed, forwarded, reserialized,
  logged, or persisted. Only a running numeric byte total is maintained,
  using overflow-safe accounting (the remaining allowance is computed before
  each addition), bounded to an **exact fixed 64 KiB
  (`64 * 1024` bytes) total per session**. Exceeding the bound fails the
  session closed without deadlock and without leaving an orphan process
  (deterministically proven by a synthetic flood-fixture smoke case).
- An invalid/out-of-range `HelperStderrPolicy` value fails closed
  (`MalformedMessage`) before any child launch.
- The runtime-smoke checker (`tools/check-mediapipe-face-landmarker-runtime-smoke.mjs`)
  was updated to accept bounded (≤ 64 KiB, measured by UTF-8 byte length,
  never JavaScript character count) opaque worker stderr instead of requiring
  it to be exactly empty, while continuing to reject any stderr over the
  bound with the existing generic `worker_protocol_invalid` reason and never
  printing, parsing, or including worker stderr content in any report.
- A second, independently discovered Windows-only contract mismatch was also
  fixed in the same checker: the real worker's own stdout report line uses
  the Windows platform line terminator (CRLF), which the checker previously
  rejected outright. The checker now strips exactly one trailing line
  terminator (LF or CRLF) while still requiring the report to be a single
  line (any remaining embedded CR or LF is rejected), preserving strict
  single-line/anti-injection behavior.

## Original Periodic MotionFrame Stall Finding and Resolution (Validation-Only)

During Part 2 browser/renderer validation, the live route exhibited a
periodic "≈5s stale / ≈2s live" oscillation. This was diagnosed to its exact
root cause with controlled comparative measurements (ephemeral timing
aggregates only; no raw MotionFrame content retained):

| Measurement | Path                                                | Duration | Frames | p50    | p95     | Max     | Gaps > 1.8s |
| ----------- | --------------------------------------------------- | -------- | ------ | ------ | ------- | ------- | ----------- |
| A1          | tracker → pipe, no `--realtime`                     | 120s     | 251    | 0 ms   | 4549 ms | 5267 ms | 21          |
| A2          | tracker → pipe, **with `--realtime`**               | 90s      | 192    | 399 ms | 454 ms  | 590 ms  | **0**       |
| B1          | full path → WebSocket client, no `--realtime`       | 60s      | 127    | 0 ms   | 4499 ms | 5943 ms | 11          |
| B2          | full path → WebSocket client, **with `--realtime`** | 60s      | 144    | 399 ms | 432 ms  | 537 ms  | **0**       |

Root cause: the tracker's native `main.cpp` only calls `std::cout.flush()`
per frame when `--realtime` is set. Without it, `std::cout` connected to a
pipe (rather than a console) is block-buffered by the C++ runtime, so
MotionFrames accumulate for several seconds before a bulk flush — a
stdout-streaming behavior, not a bridge, WebSocket, or renderer defect (the
bridge/WebSocket layers add no measurable delay of their own: B1≈A1, B2≈A2).

**Validation-only mitigation**: the local, uncommitted validation launcher
adds the existing `--realtime` flag. This is a **validation invocation
choice**, not a production code change, and **not a permanent production
fix**. A subsequent bounded, automated 120-second stability check (before any
further owner observation) confirmed: 305 frames, all `source:"native"`,
p50=318ms, p95=583ms, max=849ms, **zero** gaps > 1.8s, zero raw MediaPipe
stderr or path leakage in the captured diagnostics.

## Long-Duration Tracking Session Finding (Established Evidence)

During extended real-device operation of the same validation route (with
`--realtime` and the local pre-warm workaround), the following was observed
and independently confirmed by automated process/transport inspection:

- The route **initially tracked successfully** (owner-observed head pose,
  eyes, mouth, and expression updates during the early part of the session).
- After approximately 30 minutes of continuous operation, tracking entered a
  **persistent lost state**.
- The tracker process, the MediaPipe helper process, the bridge process, the
  camera/frame capture loop, and the WebSocket transport **all remained
  alive** throughout.
- During a 15-second automated observation window taken during the persistent
  lost state: **450 of 450** delivered MotionFrames reported
  `tracking.status:"lost"`; `tracking.confidence` **never exceeded zero**
  across the window.
- MotionFrame timestamps and the tracker's own emitted-frame counter
  continued to advance throughout (transport was live, not stale — this is
  explicitly distinguished from the separate, already-resolved periodic-stall
  finding above).
- The invocation used for this session contained **no** finite-frame limit,
  smoke-test mode, automatic-stop option, or intentional tracking timeout
  (`--continuous --realtime` only, confirmed from the live process's actual
  command line).
- The owner's attempts to restore detection (repositioning, moving back into
  frame) did **not** recover the current session.
- **Restart recovery was not verified**: two bounded restart attempts (each
  preceded by a fresh pre-warm that reported a real interpreter exit code of 0) both failed during backend startup with the existing generic
  `"Failed to start tracking backend: mediapipe-face-landmarker."` diagnostic
  category before a new session could be established. Both restart attempts
  failed with the known generic backend-start failure category. The behavior
  is consistent with the separately documented cold-start ready-timeout risk,
  but **the exact cause of these two attempts was not independently proven**.
  Because of this, it could not be determined whether a successful restart
  would have restored tracking (i.e., whether the failure is scoped to the
  single long-running process session or persists across a fresh process).
- Supporting, non-conclusive timing evidence: the tracker's own periodic
  pipeline diagnostic (`trackingDurationMs`, a per-frame timing figure,
  never raw frame/landmark content) showed a **sharp change** from an initial
  real-inference measurement of approximately 407 ms (captured earlier in a
  short validation run) to a sustained sub-millisecond-to-low-millisecond
  range (with a rare ~13 ms outlier) after prolonged operation. This timing
  change **suggests** that real inference or reacquisition work may no
  longer have been occurring during the persistent lost state; it is
  supporting evidence, not a proven root cause, and this report does not
  claim as fact that MediaPipe internally stopped performing inference.

This is recorded as a distinct, independent finding from the periodic-stall
finding above: transport-staleness fallback (searched for and ruled out here
by confirming live, advancing timestamps) is not the same as this
tracking-liveness failure, and the two must not be conflated.

## Follow-up Candidates (not created as Issues in this task)

Recorded for owner review; severity is distinguished from recommended
engineering sequence.

**A. MediaPipe cold-start readiness budget** — reliable startup and accurate
startup-failure classification during cold MediaPipe/model initialization
(the existing ready-handshake budget can be exceeded on a cold start).

**B. Native MotionFrame stdout streaming contract** — production MotionFrame
consumers should receive each complete frame promptly without depending on
an unrelated pacing flag (`--realtime`) for prompt delivery; the permanent
design needs separate review and must not be assumed to be an unconditional
`std::cout.flush()`.

**C. MediaPipe long-running tracking-session liveness (highest severity)** —
persistent lost state after extended operation while transport and all
processes remain healthy; investigation scope includes deterministic
time/frame-count correlation, helper session state after prolonged
inference, MediaPipe VIDEO/LIVE_STREAM running-mode behavior, timestamp
monotonicity/units, camera frame continuity, detection/presence thresholds,
helper-to-tracker lost-result mapping, whether the MediaPipe graph/session
needs recreation, bounded automatic recovery, and reliable reacquisition
without a full route restart.

**D. MediaPipe runtime throughput and end-to-end latency** — approximately
2.5 fps during active inference and approximately 0.5–1.0 seconds of
perceived response latency observed during validation; the native inference
cadence should be investigated separately from renderer-side smoothing
latency.

**E. Blink visual calibration** — blink is detected but the current renderer
mapping does not visually close the avatar's eyes fully.

Highest severity: **C**. Recommended engineering sequence: **A → B → C → D →
E** — A and B establish a more reliable and observable environment (accurate
startup, prompt frame delivery) before reproducing and fixing C.
