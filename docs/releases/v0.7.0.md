# v0.7.0 Release Readiness Notes

## Summary

v0.7.0 is the **MediaPipe local feasibility foundation** after the v0.6.0 local backend candidate validation spike.

This release-readiness note closes the v0.7.0 evidence pass by recording a source-grounded MediaPipe dependency and asset route decision, a disabled-by-default CMake feasibility option that fails fast at configure time when enabled, and automated checker evidence for that boundary.

v0.7.0 does **not** integrate, enable, approve, or ship MediaPipe. It does not add MediaPipe, ONNX Runtime, model/task assets, runtime downloads, inference, or production backend selection. The existing `mediapipe-face-landmarker` runtime path remains unsupported and fail-closed.

LVK remains local-first: camera frames stay local, `MotionFrame` remains stable, and backend/runtime details stay behind Native Core. Default `face-pipeline`, dummy/noop, OpenCV baseline, MotionFrame, Electron, and Web Preview boundaries remain unchanged.

## Completed slices

- #480 recorded a source-grounded MediaPipe dependency and asset feasibility route decision in `docs/TRACKING_BACKEND_V0_7_MEDIAPIPE_FEASIBILITY.md`. It found that MediaPipe Face Landmarker remains relevant because official docs describe 3D face landmarks, blendshape scores, and facial transformation matrices, but no current official desktop/C++ Face Landmarker Tasks guide was found during review. Framework C++ examples and model-bundle documentation do not prove a small supported LVK CMake integration route or settle task/model asset notice and redistribution approval. The decision approved only a no-asset, no-runtime-download feasibility boundary and did not approve production backend selection, dependencies, assets, runtime downloads, inference, MotionFrame changes, Motion Protocol changes, or Electron/Web Preview runtime dependencies.
- #481 added the optional Native Core CMake feasibility boundary `LVK_ENABLE_MEDIAPIPE_FACE_LANDMARKER_PROBE`. The option is disabled by default, normal Native Core builds remain dependency-free with respect to MediaPipe, and enabling the option intentionally fails at configure time with an explicit #480 non-approval message. This is a disabled-by-default probe option and explicit non-approval boundary, not a real MediaPipe build. #481 did not call `find_package(MediaPipe)`, add MediaPipe includes, libraries, sources, generated code, model/task/cascade assets, runtime packages, runtime downloads, inference, or `LVK_HAS_MEDIAPIPE_FACE_LANDMARKER=1`.
- #482 added automated checker evidence in `tools/check-native-mediapipe-build-feasibility-boundary.mjs` and the package script `pnpm test:native-mediapipe-build-feasibility-boundary`, then wired that checker into `pnpm test`. The checker statically verifies that the CMake option exists, defaults to `OFF`, fails fast with `FATAL_ERROR` when enabled, includes v0.7.0 / #480 non-approval categories in the message, and rejects targeted MediaPipe integration patterns. When CMake is available, it also runs a temporary configure probe and confirms the expected nonzero fail-fast result, then cleans the temporary directory.

#481 and #482 also used the explicit fail-fast configure command shape:

```bash
cmake \
  -S native/tracker-core \
  -B <temporary-or-local-build-directory> \
  -DLVK_ENABLE_MEDIAPIPE_FACE_LANDMARKER_PROBE=ON
```

The expected result is a nonzero configure exit with an explicit #480 non-approval message. This validates the feasibility boundary and is not a successful MediaPipe build.

#480 was docs-only and used `pnpm format:check`. OpenCV support was unavailable in some implementation/checker environments, and OpenCV-specific runtime output was skipped honestly where capabilities were false. No live webcam/camera path was validated. #482's checker may runtime-skip only if CMake is unavailable after static checks pass.

## Next direction

After this note merges and #483 is complete, close parent issue #479.

v0.7.0 successfully establishes a safe feasibility boundary but does not deliver tracking-quality improvement. Avoid continuing with another docs/Gate-only milestone by default. Prefer returning to a visible implementation milestone, such as calibration and avatar preview polish, visible local tracking UX improvements, or renderer/avatar integration planning backed by actual UI implementation.

Any real MediaPipe dependency/model/task/runtime integration must be a separate explicitly approved issue/PR. A future MediaPipe implementation issue must include the exact supported desktop/C++ integration route, dependency/version decision, license/notice/redistribution plan, task/model asset sourcing and packaging plan, local-only/no-runtime-download proof, MotionFrame mapping plan, rollback/fail-closed behavior, and exact validation commands and evidence.
