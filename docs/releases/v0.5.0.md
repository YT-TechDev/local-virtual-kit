# v0.5.0 Release Readiness Notes

## Summary

v0.5.0 is a **Native Core backend evaluation foundation** closeout for LVK after the v0.4.0 local runtime confidence and native pipeline readiness pass.

This release readiness note summarizes the completed Native Core backend boundary, checker evidence, and backend evaluation documentation for future local backend candidates. It does not select, approve, or add a production tracking backend. LVK remains local-first: camera frames stay local, `MotionFrame` remains stable, and backend evaluation must stay behind Native Core boundaries.

## Completed slices

- Added the Native Core `TrackingBackend` / `FaceTrackingPipelineBackend` seam so the existing detector/tracker wiring sits behind a small backend boundary without changing CLI behavior, stdout JSON behavior, or `MotionFrame` shape.
- Preserved the dummy/noop path behind the boundary as the stable local dependency-free producer.
- Preserved the optional OpenCV Haar-style baseline behind the boundary where supported, while keeping it build/runtime-aware and camera-free by default.
- Added backend parity `MotionFrame` checker coverage for stdout JSON schema compatibility across backend-boundary behavior.
- Added backend evaluation evidence notes for the v0.5.0 boundary work and future local backend candidate reviews.

## Validation performed

The v0.5.0 implementation slices added or exercised focused automated coverage for the backend boundary paths, including:

- `pnpm format:check` for repository formatting.
- `pnpm test` for the wired workspace checker sequence where implementation PRs changed source or package behavior.
- `pnpm test:native-dummy-backend-boundary` for the dummy/noop backend boundary path.
- `pnpm test:native-opencv-baseline-boundary` for the optional OpenCV Haar-style baseline boundary and fail-closed/skip behavior.
- `pnpm test:native-backend-parity-motionframe` for backend-boundary `MotionFrame` stdout JSON compatibility.
- `pnpm test:native-runtime-capabilities` for Native Core runtime capability reporting.
- Native configure/build checks where the implementation PR reports actually ran them.

OpenCV-enabled cascade-backed parity smoke is not claimed unless a trusted local cascade path and OpenCV-enabled build were actually used and recorded. Unsupported-build and no-cascade paths are valid boundary evidence, but they are not webcam, OpenCV hardware, or cascade-backed tracking validation.

This release-readiness closeout is docs-only. The docs-only note itself only requires `pnpm format:check` and does not add a new local/manual validation claim.

## Non-goals and preserved boundaries

- No `MotionFrame` schema change.
- No Motion Protocol change.
- No production backend selection, approval, or shipping claim.
- No MediaPipe, ONNX, model, task, cascade asset, runtime dependency, runtime download, generated artifact, or binary addition.
- No cloud upload, telemetry, analytics, remote inference, external frame processing, hidden network behavior, or runtime downloads.
- No raw frame IPC, pixel IPC, or tensor IPC.
- No Electron or Web Preview dependency on backend runtime packages.
- No real eye tracking, mouth tracking, expression tracking, landmark tracking, or blendshape tracking claim.

## Remaining local/manual checks

These checks remain environment-dependent and should only be marked complete when the project owner or another local operator performs them on suitable hardware/software and records the result safely:

- OpenCV-enabled cascade-backed parity smoke with a trusted local cascade path.
- Webcam/OpenCV camera validation on suitable local hardware, native build, and OS camera-permission setup.
- Electron GUI check if runtime readiness UX is intentionally revalidated.
- OBS Browser Source visual check with a local `MotionFrame` stream.
- Packaged Electron validation and runtime staging validation.
- Hardware-specific validation across machines, cameras, GPU/driver combinations, and OS permission setups.

## Next direction

After this note is merged and all v0.5.0 child issues are complete, close the #455 v0.5.0 roadmap issue.

Future work should evaluate local backend candidates using the evidence checklist in `docs/TRACKING_BACKEND_EVALUATION.md`. Candidate evaluation must remain local-first and avoid backend/runtime dependency leakage into Electron or Web Preview. No new backend dependency, model, runtime, task, cascade asset, generated artifact, binary, or runtime download should be added without a separate scoped issue and PR.
