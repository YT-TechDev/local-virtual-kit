# v0.14.0 Release Readiness Notes

## Summary

v0.14.0 is the **Desktop Real Tracking Workflow** release. It connects the
existing opt-in Native Core MediaPipe Face Landmarker development route to the
Electron development workflow without changing the MotionFrame v1 contract or
moving camera, tracking, or helper ownership out of Native Core.

Electron now provides a fixed tracking-backend selector, persists only the
approved backend token, validates the required local development configuration
in the main process, launches the existing Native Core route through typed IPC
and argument-array spawning, and exposes only fixed backend and route-readiness
categories to the renderer and copied diagnostics. The default remains
`face-pipeline`; `mediapipe-face-landmarker` remains an explicitly selected,
development-only route that requires the OpenCV camera source.

On the owner's Windows development machine, the complete Electron -> Native
Core -> MediaPipe helper -> MotionFrame bridge -> Web Preview workflow was
accepted after a bounded real-device validation. The owner observed tracking,
intentional face loss, same-session reacquisition, head rotation, eye movement,
mouth movement, continued response after reacquisition, the explicit Stop path,
and normal application-quit cleanup.

This release does not select a production backend, bundle Python, MediaPipe, or
a model asset, provide runtime downloads, prove packaged-application readiness,
approve tracking performance, or prove the long-running reliability defect in
#586/#589 fixed.

## Completed slices

### #595 / PR #600 - typed launch contract

This slice added the closed `NativePipelineTrackingBackend` union with exactly
`face-pipeline` and `mediapipe-face-landmarker`, extended the typed start options
and existing IPC parser, and preserved `face-pipeline` as the omitted-option
default with unchanged default arguments.

For the MediaPipe route, Electron main requires the OpenCV camera source, reads
the local Python interpreter and model-asset configuration from the two
approved environment-variable keys, derives the repository-owned helper script
location, validates all three files before starting the bridge or tracker, and
appends each existing Native Core MediaPipe flag exactly once. Native Core is
still spawned with an argument array and `shell: false`.

All validation failures use fixed messages. Private configuration values,
resolved paths, argv, raw filesystem errors, and exception text are not added to
renderer state, persisted settings, runtime status, or copied diagnostics.

### #596 / PR #601 - persisted development controls

This slice added `trackingBackend` to `DesktopRuntimeSettings`. Missing, legacy,
malformed, or unsupported values normalize to `face-pipeline`; only one of the
two fixed backend tokens is persisted.

The existing Electron Runtime controls now contain one accessible backend
selector with `Face pipeline` and `MediaPipe Face Landmarker (development)`
choices. The MediaPipe choice requires the OpenCV camera source. Incompatible
state disables both Start actions and produces an accessible fixed explanation,
without silently rewriting the camera source, detector, index, FPS, resolution,
or backend setting.

Both Start paths forward the selected fixed token through the existing typed IPC
channel. No Python, model, helper, repository, argv, or environment-value field
was added to persisted settings or renderer state.

### #597 / PR #602 - sanitized route status

This slice extended `LvkRuntimeStatus` with the selected/last-attempted fixed
backend and one closed route-readiness category:

- `not-applicable`
- `unchecked`
- `ready`
- `incompatible-camera-source`
- `python-unavailable`
- `model-unavailable`
- `helper-unavailable`

The renderer maps these tokens to fixed human-readable labels in the runtime
summary, detailed status, and copied diagnostics. `ready` is displayed as
`Configured`; it proves that the MediaPipe-specific preflight passed, not that a
later native process or camera operation must succeed.

The focused checker includes synthetic sentinel private values and a negative
control to prove that private path-shaped values do not reach representative
renderer-facing artifacts. This is source-contract evidence, not a substitute
for Electron, camera, MediaPipe, or Web Preview execution.

### #603 / PR #604 - Windows development runtime adjacency

The first #598 attempt exposed a pre-`main()` Windows Native Core failure when
required OpenCV runtime DLLs were not available through the inherited process
environment. Two proposed mechanisms were rejected by audit and real execution:
CMake's resolved runtime-DLL closure omitted required transitive vcpkg DLLs, and
a caller-controlled `VCPKG_APPLOCAL_DEPS` cache value could not prove that the
vcpkg app-local hook was engaged.

The accepted contract proves the artifact instead of attempting to attest its
toolchain. For Windows OpenCV-enabled Native Core development builds, the
default/ALL build includes a mandatory post-build execution gate. It starts the
exact generated configuration from its output directory with a minimal Windows
system PATH and requires a successful, local-only capability response without
opening a camera or emitting MotionFrame-shaped output. Failures are reduced to
fixed safe categories.

Explicit-target or direct IDE executable-project builds can bypass that ALL
target. They remain incomplete for runtime-adjacency proof until the matching
explicit-configuration local checker passes. OpenCV-disabled Windows builds,
non-Windows builds, and packaged runtime staging remain outside this development
gate.

Electron itself was not changed by #603 and still consumes the development
Native Core build without learning vcpkg or OpenCV layout details.

## Development-only configuration

The MediaPipe route is configured outside persisted Electron settings:

- Electron main reads the local Python interpreter from
  `LVK_MEDIAPIPE_SMOKE_PYTHON`.
- Electron main reads the local model asset from
  `LVK_MEDIAPIPE_MODEL_ASSET_PATH`.
- Electron derives the helper script from the repository-owned fixed location.
- Only the fixed backend token is persisted and sent through renderer-facing
  settings.
- Required paths are passed directly to the Native Core child through the
  existing argument array with `shell: false`.

No private value or resolved local path is included in this document. The
Python environment, MediaPipe package, model asset, and local dependency layout
remain owner-supplied development prerequisites and are not committed, bundled,
downloaded, or distributed by LVK.

## Architecture and privacy boundaries

Native Core remains the sole owner of camera capture, tracking, helper lifecycle,
private frame/control/result IPC, mapping, and MotionFrame production. Electron
owns the fixed development selector, sanitized preflight and status, native
argument construction, and process lifecycle. Web Preview remains
backend-agnostic and consumes MotionFrame only.

MotionFrame remains at `schemaVersion: 1`. No backend, helper, runtime path,
landmark array, transformation matrix, complete blendshape collection, or
private diagnostic field was added to MotionFrame or the localhost WebSocket
messages.

Camera frames remain local. v0.14.0 adds no telemetry, analytics, cloud upload,
remote inference, external frame processing, runtime downloads, hidden network
behavior, persistent frame storage, MotionFrame history, or raw tracking-history
persistence.

## Known limitations and open risks

- The MediaPipe backend remains opt-in and development-only;
  `face-pipeline` remains the backward-compatible default.
- Python, MediaPipe, the helper runtime prerequisites, and the model asset are
  not bundled, installed, downloaded, or updated by LVK.
- Packaged Electron distribution and installer behavior are not implemented or
  validated by this release.
- OBS Browser Source was not exercised during #598 and is not claimed.
- The accepted real-device configuration used camera index 0. Issue #605 proved
  a camera-start failure with index 1 and a later successful open with index 0,
  but did not prove the root cause, automatic fallback, device enumeration,
  permission behavior, or an exact internal OpenCV false-return boundary.
- The normal-quit result is owner-observed and supported by the focused
  lifecycle check, but its separate live run lacks a formal pre-intervention
  process/port snapshot.
- MediaPipe inference accuracy, MotionFrame numerical accuracy, throughput,
  latency, CPU/memory behavior, and final calibration quality were not approved.
- No 45-60 minute post-fix reliability soak was performed for v0.14.0.
- #586 and #589 remain open. Their preserved classifications are: deterministic
  terminal-failure detection and bounded recovery mechanics are proven by
  focused native smokes; a natural long-running ResultTimeout was reproduced
  previously; recovery correctness during a future natural occurrence remains
  unknown; and the long-running defect is **not claimed fixed**.
- Multiple faces, body tracking, hand tracking, GPU optimization, production
  backend selection, and final arbitrary-avatar facial-rig compatibility remain
  outside this release.

## Release-readiness conclusion

The merged implementation and accepted #598 evidence satisfy the v0.14.0
Desktop Real Tracking Workflow development milestone at the current `main`
revision. This documentation change does not itself create a tag, publish a
GitHub Release, approve production packaging, or close #599, parent #594, or
Milestone #15. Those closeout actions belong after this documentation PR is
reviewed, merged, and reverified.
