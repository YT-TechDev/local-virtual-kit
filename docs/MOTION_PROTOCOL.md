# MotionFrame Protocol

## 1. Purpose

MotionFrame is the shared protocol between the C++ Native Tracking Core and the R3F Avatar Preview.

It must remain small, normalized, framework-independent, transport-friendly, and independent from React, Three.js, React Three Fiber, Electron UI internals, OpenCV, MediaPipe, and native platform APIs.

The Native Core estimates tracking values and emits MotionFrame objects. The renderer consumes MotionFrame objects and maps them to avatar motion.

MotionFrame is a data contract, not a rendering contract.

## 2. Schema Version

v0.1 uses `schemaVersion: 1`.

Breaking changes must increment `schemaVersion` and update all related protocol producers and consumers together.

When changing MotionFrame, update:

- `packages/motion-protocol`
- dummy frame generation
- R3F renderer mapping
- Native Core serializer draft or implementation
- this document

## 4. Field Rules

### `schemaVersion`

The protocol version for the frame shape.

v0.1 must emit `1`.

### `timestampMs`

Frame timestamp in milliseconds.

The value should be monotonic from the producer's perspective when possible.

### `source`

The source of the MotionFrame.

Allowed values:

- `dummy`: generated by the TypeScript dummy frame helper.
- `native`: emitted by the C++ Native Tracking Core.

### `tracking`

Tracking status and confidence.

```ts
tracking: {
  status: "not_started" | "tracking" | "lost";
  confidence: number;
}
```

Rules:

- `status: "not_started"` means tracking has not started yet.
- `status: "tracking"` means a face is currently being tracked.
- `status: "lost"` means tracking was active but the face is currently lost.
- `confidence` should be normalized from `0.0` to `1.0`.

`tracking.status` replaces the older `face.detected` style because it can represent more states than a boolean.

### `face.position`

Normalized face position.

```ts
face: {
  position: {
    x: number;
    y: number;
    z: number;
  }
}
```

Rules:

- `x`: horizontal face position.
- `y`: vertical face position.
- `z`: depth-like normalized value.

The exact camera-space to normalized-space conversion may evolve, but renderer-facing values should remain stable and documented.

### `face.rotation`

Head rotation values.

```ts
face: {
  rotation: {
    pitch: number;
    yaw: number;
    roll: number;
  }
}
```

Rules:

- `pitch`: up/down head rotation.
- `yaw`: left/right head rotation.
- `roll`: head tilt rotation.

The renderer is responsible for mapping these values into avatar-specific rotation ranges.

### `eyes`

Eye openness and gaze state.

```ts
eyes: {
  leftOpen: number;
  rightOpen: number;
  gaze: {
    x: number;
    y: number;
  }
}
```

Rules:

- `leftOpen`: normalized `0.0` to `1.0`.
- `rightOpen`: normalized `0.0` to `1.0`.
- `gaze.x`: normalized horizontal gaze direction.
- `gaze.y`: normalized vertical gaze direction.

Blink should be derived from `leftOpen` and `rightOpen` in the renderer or mapping layer when needed.

Do not add a separate `blink` field in v0.1 unless the producer and renderer need a non-derivable blink signal.

### `mouth`

Mouth expression values.

```ts
mouth: {
  open: number;
  smile: number;
}
```

Rules:

- `open`: normalized `0.0` to `1.0`.
- `smile`: normalized `0.0` to `1.0`.

v0.1 uses `mouth.open` and `mouth.smile` for basic expression mapping. Full emotion estimation is out of scope for the initial protocol.

## 5. C++ Structure Draft

The C++ side does not need to mirror the TypeScript object layout exactly, but it must serialize into the same MotionFrame JSON shape.

```cpp
enum class MotionFrameSource {
  Dummy,
  Native
};

enum class TrackingStatus {
  NotStarted,
  Tracking,
  Lost
};

struct Vector2 {
  float x;
  float y;
};

struct Vector3 {
  float x;
  float y;
  float z;
};

struct EulerRotation {
  float pitch;
  float yaw;
  float roll;
};

struct TrackingQuality {
  TrackingStatus status;
  float confidence;
};

struct FacePose {
  Vector3 position;
  EulerRotation rotation;
};

struct EyeState {
  float leftOpen;
  float rightOpen;
  Vector2 gaze;
};

struct MouthState {
  float open;
  float smile;
};

struct MotionFrame {
  int schemaVersion;
  double timestampMs;
  MotionFrameSource source;
  TrackingQuality tracking;
  FacePose face;
  EyeState eyes;
  MouthState mouth;
};
```

When serialized to JSON, enum values must use the TypeScript string values:

```json
{
  "schemaVersion": 1,
  "timestampMs": 0,
  "source": "native",
  "tracking": {
    "status": "tracking",
    "confidence": 1
  },
  "face": {
    "position": {
      "x": 0,
      "y": 0,
      "z": 0
    },
    "rotation": {
      "pitch": 0,
      "yaw": 0,
      "roll": 0
    }
  },
  "eyes": {
    "leftOpen": 1,
    "rightOpen": 1,
    "gaze": {
      "x": 0,
      "y": 0
    }
  },
  "mouth": {
    "open": 0,
    "smile": 0
  }
}
```

## 6. Transport

v0.1 uses WebSocket + JSON for local transport.

The renderer should tolerate:

- missing frames
- disconnects
- reconnects
- delayed frames
- out-of-order frames
- out-of-range values
- `tracking.status = "not_started"`
- `tracking.status = "lost"`

The renderer should clamp or safely ignore values that are outside expected ranges.

Camera frames must be processed locally. Camera frames must not be sent to external servers in v0.1.

## 7. Dummy MotionFrame

`motion-protocol` must provide dummy frames for renderer development without native tracking.

Dummy frames should:

- use `schemaVersion: 1`
- use `source: "dummy"`
- use `tracking.status: "tracking"` when simulating active tracking
- animate face position
- animate face rotation
- animate eye openness
- animate gaze
- animate mouth open
- animate smile

Dummy frames are development tools. They must not become renderer-specific.

## 8. Renderer Mapping Policy

The renderer should treat MotionFrame as input data and map it into avatar-specific motion.

The renderer may derive additional values such as:

- blink
- idle motion
- smoothed head rotation
- expression blend values
- avatar-specific bone rotations
- avatar-specific morph target weights

These derived values should not be added to MotionFrame unless they are required as shared protocol data between Native Core and Renderer.

## 9. Compatibility Policy

Avoid breaking MotionFrame after the first working MVP.

If a breaking change is needed, update all of the following in the same PR:

- protocol TypeScript types
- dummy frame generator
- R3F renderer mapping
- Native Core serializer draft or implementation
- this document

Renderer code should prefer tolerant parsing and safe defaults where possible.
